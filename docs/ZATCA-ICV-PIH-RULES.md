# ZATCA ICV and PIH Sequence Rules

## Overview

This document clarifies the critical rules for **Invoice Counter Value (ICV)** and **Previous Invoice Hash (PIH)** sequences in ZATCA Phase 2 e-invoicing.

## Key Rules (Verified from ZATCA)

### 1. ICV is Sequential Per CSID (Not Per Document Type)

**IMPORTANT**: ICV counter is shared across ALL invoice types for a single CSID:
- Standard Invoice
- Standard Credit Note
- Standard Debit Note
- Simplified Invoice
- Simplified Credit Note
- Simplified Debit Note

**Correct Example:**
```
ICV 1: Standard Invoice
ICV 2: Simplified Invoice
ICV 3: Standard Credit Note
ICV 4: Simplified Debit Note
ICV 5: Standard Invoice
```

**WRONG Example (separate counters):**
```
Standard Invoice: ICV 1, 2, 3...
Simplified Invoice: ICV 1, 2, 3...  ← WRONG!
```

### 2. PIH Chain is Also Per CSID

The PIH (Previous Invoice Hash) forms a continuous chain across ALL documents:

```
Invoice 1 (ICV=1): PIH = default hash
Invoice 2 (ICV=2): PIH = hash of Invoice 1
Invoice 3 (ICV=3): PIH = hash of Invoice 2
```

The chain must be unbroken regardless of:
- Invoice type (B2B, B2C)
- Document type (Invoice, Credit Note, Debit Note)
- Success/failure status (rejected docs still count!)

### 3. One Certificate Per Company is Sufficient

- You do NOT need individual certificates for each user
- One CSID per company/server is typically enough
- Multiple EGS devices = multiple CSIDs = multiple sequences

### 4. Several EGS Units per Taxpayer

ZATCA's E-Invoicing Detailed Guidelines say, of one taxpayer running several
devices:

- "An E-Invoice Solution may contain one or more Units" (p9, 2.7).
- The Fatoora portal onboards "the user's EGS Unit through generating
  cryptographic stamp identifier", and a CSID links the unit to a trusted
  third party to "uniquely identify their unit" (p10, 2.8 and 2.10).
- Taxpayers "Register the E-Invoice Solution Units used for generating
  E-Invoices" (p39), and "every device issuing invoices with the same VAT
  number should be registered" (FAQ, p59).
- "The E-Invoice Solution unit must not generate more than one sequence so
  that all invoices generated by an E-Invoice Solution Unit are linked using
  'Previous Invoice Hash' value into a single chain" (p28 and p35).
- The counter may not be reset, and is protected from users (p25, 5.4).
- The invoice reference number "may be different, for example, a different
  sequential reference number for each branch" (p11, 2.14).

So each unit - each till - holds its own CSID, counter and chain, and two
tills selling at once never share either.

| Scenario | Certificate Approach |
|----------|---------------------|
| Single location | One CSID, one ICV sequence |
| Multiple branches, central server | One CSID, one ICV sequence, different "Other Seller ID" per branch |
| Multiple branches, independent | Separate CSID per branch, each with own ICV sequence |
| Several tills in one branch | Separate CSID per till, each with own ICV sequence and PIH chain |

**For central server with branches:**
- Use the same CSID
- Populate `cac:PartyIdentification` with branch-specific CR/MOMRAH license
- Populate `cac:PostalAddress` with branch address
- VAT number remains the same (company-wide)

### 5. Rejected Documents Still Count

**CRITICAL**: Even if ZATCA rejects an invoice:
- The ICV is consumed (don't reuse it)
- The document hash enters the PIH chain
- Next document must reference the rejected document's hash

```
Invoice 1 (ICV=1): ACCEPTED → hash = ABC123
Invoice 2 (ICV=2): REJECTED → hash = DEF456
Invoice 3 (ICV=3): PIH = DEF456 (hash of rejected Invoice 2)
```

## Implementation in This Codebase

### Units (tills)

Every device is a row of `egs_units` (`App\Domains\Organization\Models\EgsUnit`):
head office's under the organization's own id with no branch, each branch's
first till under the branch's own id, and any till added later under an id
of its own - so the devices that existed before units were kept apart
carried on with the same chain, credentials and numbering. `invoices.device_id`
refers to the unit. A unit's `host` is `cloud` for now; a store's edge node
will add `edge`.

An invoice is issued on the till its request named (`till_id`, or
`till_number` within `branch_id`), else on its branch's default till - a
ready one first - else on head office's. The till is the issuing lock's
scope, the counter and chain, the credential store's directory (by
certificate version) and the numbering series. Each till is onboarded with
its own OTP (`UnitOnboarding`), and its CSR's serial number is the unit's
`egs_serial`. A till is retired (`UnitRetirement`) only once nothing it
signed is left to file; until then it is `retiring` and issues nothing new,
and a retired till never issues again - the issuing step asks again under
the till's lock. `TillChainTest` and `TillConformanceTest` (through ZATCA's
SDK) hold two tills of one branch interleaving with a chain each.

### One lock for counter, number and chain

Issuing runs through the shared `App\Domains\Invoice\Services\IssuingLifecycle`,
which holds the issuing lock of the document's device - a row of
`issuing_locks`, one per device, named by the Saudi step's `lockScope()` -
for the whole issue. Inside that lock, in this order:

1. **ICV:** the Saudi step (`Countries/SaudiArabia/Issuing/IssuingStep::beforeNumbering`)
   allocates the next counter with `Invoice::generateNextIcv()`, per device - the
   till it is issued on when that till holds a certificate, head office otherwise
   - because ZATCA keeps one counter and one chain per EGS unit.
2. **Invoice number and moment of issue,** set by the lifecycle.
3. **PIH and the signed document:** the step reads the previous invoice's hash,
   builds and signs the XML, and the lifecycle saves the hash, QR and document
   with the status in one update.
4. **Chain entry:** `Countries/SaudiArabia/Issuing/ChainRecorder` records the
   invoice's hash and its predecessor, with the certificate that signed it.
   That certificate is what files the document: a device keeps every
   production certificate it has held as a version, keyed by the same digest,
   and a document still queued or reported late after a renewal is filed with
   the version that signed it, not the device's new one (see
   COMPLIANCE-POLICIES.md, section 8).

Because the counter, the number and the chain entry are decided under the same
lock, two issuances for one device cannot claim the same predecessor. Devices
have separate counters and chains, so two devices - two tills of one company -
issue at the same time. Each till (branch) numbers from a series of its own
by default - the organization's pattern with its till number in it, such as
`INV-T01-{YYYY}-{SEQ}` - so tills do not wait for each other for a number
either. An organization that chooses one shared series (Numbering in the
portal) has its tills wait for each other while the number is taken and until
their issuance commits. Two series never share a pattern.
There is no separate counter store: a failure rolls the counter back with
everything else. `php artisan fatoora:verify-hash-chain` checks a chain end to
end.

### Default PIH

For the first invoice in a chain, use the ZATCA SDK default PIH:
```
NWZlY2ViNjZmZmM4NmYzOGQ5NTI3ODZjNmQ2OTZjNzljMmRiYzIzOWRkNGU5MWI0NjcyOWQ3M2EyN2ZiNTdlOQ==
```

This is a base64-encoded SHA-256 hash of a zero value.

## Compliance Checklist

- [ ] ICV increments by 1 for every document (regardless of type)
- [ ] ICV never reused (even for rejected/void documents)
- [ ] PIH references the immediately previous document's hash
- [ ] PIH chain includes rejected documents
- [ ] One ICV sequence per CSID
- [ ] One CSID, ICV sequence and PIH chain per till (EGS unit), several per branch allowed
- [ ] A retired till issues nothing again
- [ ] Branch invoices have correct "Other Seller ID" and address
